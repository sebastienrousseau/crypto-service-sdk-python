# ADR 0001: A thin client over crypto-server

- Status: accepted
- Date: 2026-11-15

## Context

Crypto Service's cryptography lives in crypto-lib, behind crypto-server's
REST API, where keys are held, algorithms are reviewed and the
conformance kit pins behaviour. A Python SDK could reimplement some
primitives locally (hashing, verification) to save a round trip.

## Decision

The SDK implements no cryptography. Every method is one HTTP call to
crypto-server, and returns what the server answered. The SDK encodes
`bytes` arguments as the API names them (hex or base64) and nothing
else; it never derives, verifies, encrypts or decrypts. The only
randomness it produces is retry jitter and W3C trace IDs.

## Consequences

- One implementation of each algorithm, in the server; the SDK cannot
  disagree with it, and the conformance kit proves the wire contract.
- Every operation needs a reachable server and costs a round trip.
- Keys and plaintexts passed to the SDK travel to the server: callers
  must use `https://` off loopback (README, Security).
- Private keys generated by the server stay there: methods take a
  `keyId`.
